# HallBookingAPI

REST API для управління бронюванням та орендою конференц-залів. Дозволяє клієнтам шукати вільні зали, бронювати та розраховувати вартість оренди в залежності від часу та обраних додатковихпослуг.

## Архітектура

Проєкт побудований за принципом Separation of Concern з елементами Clean Code:

```
Controllers/        → HTTP-ендпоінти, приймають запити та повертають відповіді
UseCases/            → бізнес-логіка, один клас — одна операція (Create, Update, Delete, Search…)
Entities/            → доменні моделі (Hall, Booking, Service) з власною валідацією
ValueObjects/         → об'єкти-значення для валідації окремих полів (назва, дата, ціна тощо)
Persistence/          → DbContext, репозиторії для роботи з базою даних
Errors/               → довідник помилок для кожної сутності
Exceptions/           → кастомні винятки (ValidationException, NotFoundException)
DTOs/                 → об'єкти для передачі даних у відповідях API
```

**Чому саме так:**
- Кожна сутність створюється тільки через, що гарантує, що невалідований об'єкт просто неможливо створити
- Бізнес-правила ізольовані в UseCases, де кожен клас відповідає за одну операцію, що спрощує підтримку та тестування
- Помилки обробляються через middleware UseExceptionHandler, що повертає клієнту зрозумілі HTTP-коди замість 500-х помилок

## Як запустити проєкт

### Вимоги
- .NET 10 SDK
- (опційно) інструмент `dotnet-ef` для міграцій:
  ```bash
  dotnet tool install --global dotnet-ef
  ```

### Інструкція

1. Клонувати репозиторій:
   ```bash
   git clone <посилання-на-репозиторій>
   cd HallBookingAPI
   ```

2. Застосувати міграції:
   ```bash
   dotnet ef database update
   ```

3. Запустити проєкт:
   ```bash
   dotnet run
   ```

4. Відкрити Swagger UI в браузері:
   ```
   http://localhost:5000/swagger
   ```

При першому запуску база даних автоматично заповнюється початковими даними (3 зали та 3 послуги) через HallDbSeeder.

## Основні ендпоінти

### Зали (Halls)
| Метод | Ендпоінт | Опис |
|---|---|---|
| `POST` | `/api/halls` | Створити новий зал |
| `GET` | `/api/halls` | Отримати список усіх залів |
| `GET` | `/api/halls/{id}` | Отримати зал за ID |
| `PUT` | `/api/halls/{id}` | Оновити інформацію про зал |
| `DELETE` | `/api/halls/{id}` | Видалити зал (заборонено, якщо є активні бронювання) |
| `GET` | `/api/halls/available` | Пошук доступних залів за датою, часом і місткістю |

### Послуги (Services)
| Метод | Ендпоінт | Опис |
|---|---|---|
| `POST` | `/api/services` | Створити нову додаткову послугу |
| `GET` | `/api/services` | Отримати список усіх послуг |

### Бронювання (Bookings)
| Метод | Ендпоінт | Опис |
|---|---|---|
| `POST` | `/api/bookings` | Забронювати зал з розрахунком вартості |

### Звіти (Reports)
| Метод | Ендпоінт | Опис |
|---|---|---|
| `GET` | `/api/reports/revenue-by-hall` | Виручка та кількість бронювань по кожному залу |

Повний перелік параметрів та схем запитів/відповідей доступний у Swagger UI.

## Розрахунок вартості оренди

Вартість формується з двох частин:
1. **Базова вартість залу**, помножена на кількість годин, з урахуванням часових поясів:
   - Ранкові години (06:00–09:00) — знижка 10%
   - Стандартні години (09:00–12:00, 14:00–18:00) — базова ціна
   - Пікові години (12:00–14:00) — націнка 15%
   - Вечірні години (18:00–23:00) — знижка 20%
2. **Вартість обраних додаткових послуг** (фіксована сума за кожну послугу).

Якщо бронювання охоплює декілька часових поясів (наприклад, з 17:00 до 19:00), вартість розраховується окремо для кожного відрізка часу.

## Валідація та обробка помилок

- Усі вхідні дані валідуються на рівні Value Objects (наприклад, назва залу не може бути порожньою, дата бронювання не може бути в минулому).
- Помилки повертаються у форматі:
  ```json
  { "error": "Опис помилки" }
  ```
- Коди відповідей:
  - `400 Bad Request` — помилка валідації вхідних даних
  - `404 Not Found` — сутність не знайдена
  - `409 Conflict` — конфлікт бізнес-логіки (наприклад, зал вже заброньований на цей час)

## Можливі напрямки розвитку

- Захист від одночасного бронювання одного й того ж часу
